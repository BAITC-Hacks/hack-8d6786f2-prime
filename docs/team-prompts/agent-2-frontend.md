## Что уже есть

React + TypeScript + Vite, согласованный светлый дизайн, основная форма подбора и карточки. Новые заготовки: `src/PlatformPages.tsx`, `src/platform.ts`, `src/platform.test.ts`, дополнения в `App.tsx`, `contracts.ts`, `styles.css`. Не считай их готовыми без проверки.

В обычном режиме все запросы идут в настоящий API; моки включаются только явно для разработки. Backend по умолчанию 8000, frontend 5173. Для изолированных проверок Vite получает `BACKEND_URL` с адресом тестового backend. Никаких OpenAI/NVIDIA-ключей в браузере.

## Обязательные пользовательские сценарии

### 1. Основной подбор и альтернативы

Сохрани все исходные поля, статусы matched/no_category/no_match, максимум три основных карточки, порядок сервера, объяснения, synthetic и примечания о дополненных данных.

При `no_match` сервер может вернуть до трёх `alternatives`. Это отдельные варианты с изменёнными условиями, а не точные совпадения. Покажи:

- имя, услугу, цену, описание и предложенную свободную дату;
- каждое отличие `requested → proposed` и его причину;
- явное пояснение, что исходные условия не выполнены;
- кнопку «Применить условия…», которая меняет поля и требует отдельного нового поиска.

Не называй занятого на исходную дату специалиста свободным на неё. Не меняй молча город/категорию/формат и не подмешивай альтернативы в число точных совпадений. Пустой массив alternatives допустим. Проверь, что существующая подсказка смены даты и новый интерфейс не ломают друг друга; согласуй изменения ожидаемого UI с агентом 3.

### 2. Публичная анкета подрядчика

Отдельная страница и понятная навигация «Подбор / Подрядчикам / Администратору».

Поля: имя/название, город, категории, форматы мероприятий, языки, описание, стартовая цена за мероприятие, максимальная длительность, занятые даты, контактный email, пометка вымышленной тестовой анкеты. Значения справочников и календарь только из API.

После отправки показывай номер анкеты и «На проверке». До одобрения анкета не появляется в подборе. Пароли подрядчиков не собираются; email не выводится заказчикам. Запрети двойную отправку, показывай ошибки полей, сети и повторной анкеты. Ошибка не должна уничтожать введённые данные.

Сделай календарь/ввод занятых дат понятным: формат, допустимый диапазон, повторы и ошибочные даты должны быть объяснены. Backend-правило уже реализовано в `contracts/platform-v2.md`: null или отсутствие `max_hours` разрешены, только если все категории входят в `Флорист`, `Декоратор`, `Подарки и сувениры`. Любая другая категория, включая смешанный выбор ведущего и декоратора, требует числа >0 и <=24. Ошибка 422 имеет loc `["body","max_hours"]`. Синхронизируй обе формы и их подсказки. Пустота означает неприменимость присутствия, а не неограниченные часы.

### 3. Административная панель

Вход по серверному коду доступа. Поле типа password, токен только в памяти текущей страницы; без URL, localStorage/sessionStorage, console.log и сохранения в анкетах. Выход очищает токен и приватные данные. После обновления страницы требуется новый вход. Никакого отображения токена после входа.

Администратор должен видеть все анкеты, включая исходные профили, их статус, происхождение и признаки данных. Нужны счётчики, фильтры статуса, пагинация, просмотр полного профиля и контакта, одобрение, отклонение с причиной, добавление нового профиля и удаление.

Перед удалением — доступное окно подтверждения с именем конкретной анкеты. При 409 не повторяй действие автоматически: предложи обновить данные. Состояния 401/403/404/409/422/503 должны быть понятны. Отменённый/запоздавший запрос не должен возвращать приватные данные после выхода или заменять свежий список.

## Валидация и этапы

1. Установи зависимости по lockfile (`pnpm install --frozen-lockfile`). Если после неполной установки не находится zod, сначала восстанови установку, а не обходи типизацию через any.
2. Проверь типы API и валидацию форм по `contracts/platform-v2.md`; backend остаётся окончательным источником правил.
3. Доведи публичную анкету и её ошибки; сделай тематический коммит.
4. Доведи админ-панель, доступ, действия, конфликты и удаление; отдельный коммит.
5. Проверь альтернативы и регрессии исходного подбора; отдельный коммит.
6. `pnpm test`, `pnpm typecheck`, `pnpm build`. Не отключай strict/проверки, чтобы получить зелёный результат.
7. Вместе с агентом 3 проверь реальные API на временной базе. Не создавай/удаляй тестовые анкеты в рабочем каталоге капитана.
8. Визуально проверь 390 и 1440 px, клавиатуру, фокус, подписи, ошибки, длинные названия и доступность. В черновике уже находили пограничный контраст подписи synthetic — повторно проверь исправление.
